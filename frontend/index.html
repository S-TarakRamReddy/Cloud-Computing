Why are the features anonymised — and is that a problem?
What V1–V28 are

The dataset publisher turned the original card and transaction details into 28 numeric components (a PCA transformation) before release. The model never sees names, card numbers or merchants; it only sees numbers that describe patterns of behaviour.

Why that is useful in a cloud design
  • Privacy by design: a bank can keep identifying data in its own systems and send only anonymised vectors to a cloud scoring service, which limits what a breach or a cloud provider could expose.
  • Data minimisation: sending the least data that does the job fits GDPR and PCI-DSS expectations.
  • Shareable: anonymised vectors can be used across institutions and for research without revealing customers.
The honest trade-off

Anonymised inputs mean the explanation says which pattern drove a decision (for example "V14 is strongly negative"), not a plain-language reason such as "unusual foreign merchant". In a real deployment the bank, which owns the transformation, can map components back to named signals internally.

How this dashboard keeps the model from being a black box
  • Every verdict shows the signals that pushed it each way.
  • The what-if explorer lets you test the model's behaviour yourself.
  • Probabilities are calibrated, so 90% means roughly 90%.
  • Honest mode and the uncertainty ranges show where it fails.
